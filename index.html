Three-minute overview, with narration.

Can a humanoid pick the right tool and then use it, standing still or on the move? 18 tasks, 55 tools and 3.1k human demonstrations, in simulation and on a real Unitree G1.

Setup

  • CAP, Code-as-Policies. One camera image in, one Python program out. It runs without the model, with up to three tries per episode.
  • RUA, Robot-Use Agent. One command at a time. The model reads each result before choosing the next.
  • Models. Claude Opus 5.5, GPT-6.1 Sol and GPT-6 Astra. 3 episodes per task, 60 s of robot motion each.
  • Commands. Inverse kinematics, finger poses, walking and a tool locator. The docs give a recipe for picking a tool up, and none for using it.

Main questionDoes a zero-shot agent beat a policy trained on the task?

At picking the tool up, yes. At using it, no. With RUA, Sol and Astra lift the right tool in every L0 episode. At L1 and L2, 1 of 216 agent episodes succeeds, while FastWAM finishes 57 to 86% of the standard L1 tasks.

Question 1How do CAP and RUA differ, and the models?

  • CAP fixes every decision in code. Sol and Astra add checks that stop the program when the solver does not converge. That flag is noisy, so their programs stop before the hand closes.
  • RUA decides step by step. The same models read the same warning, carry on, and pick the tool up every time. Their fixes stay local, and each retry costs time.
  • Opus 5.5 looks often and changes plan, which gave the one L1 success. It also gives up early, and it is the only model that picked the wrong tool.
  • GPT-6.1 Sol follows the recipe exactly and reports symptoms, not causes.
  • GPT-6 Astra behaves like Sol at about eight times the cost.

Question 2How far do agents get, and where is the bottleneck?

The tool usually reaches the hand and the target, and no further. The hand fails first, then the reasoning does not change course.

  • Tool choice. Mostly right, even when the detector mislabels a tool. The exception: with a decoy in BallRetrieve L2, Opus took the straight stick over the hook in 2 of 3 episodes, so it could push the ball but never pull it back.
  • Grip. A one-hand pinch lets the tool rotate or fall while it is carried.
  • Tool tip. Agents place the hand, not the tip, so sweeps and strikes miss.
  • Force. Slow strikes do not break ice. One fast swing did, and the hammer left the hand.
  • One hand. The left hand does everything, even when the goal is on the right.
  • No change of strategy. The symptom is named, then the same approach is retried.

Question 3How long does it take, and what does it cost?

An episode holds 60 s of robot motion. With the wait for model responses, its runtime reaches 6 to 23 minutes, which works only because the simulation waits. An episode costs $0.29 to $3.86.

Takeaway

LLM agents choose the tool and plan. Three problems remain.

  • Low-level control. A one-hand pinch slips while carrying or striking, commands set position but not force or speed, and walking with a tool drifts.
  • Reasoning. Agents name the symptom, then retry the same approach. They get no feedback while a command runs, and they use the same order every time.
  • Time. An episode takes up to 23 minutes for 60 s of motion.

KYO's insight

  • A low-level control model is needed. GUI agents needed little physical knowledge, and time did not matter. Tool use needs both. However good the LLM, it needs a separate model for low-level control. Whether that is classical control such as PD and IK or a neural action generator such as a VLA is still open. An LLM that could handle force and walking itself would solve this, but running a large LLM for every contact is wasteful. A model specialized in control is the better split. People work this way too: we decide what to do without reasoning through every muscle.
  • The reasoning failures are harness problems. Keeping the same strategy comes from implementation, not from the model: the agent has no memory of what it tried before. Getting no feedback during a command and repeating the same order are limits of the agentic pipeline too. The harness should supply that memory and that feedback.
  • Time alone calls for System 2 and System 1. A real robot does not wait 23 minutes. A slow planner and a fast controller have to run together.

The task structure in one figure
What the policy sees and controls
  • Robot. Unitree G1 with 29 body joints, two seven-joint Dex3 hands and a head camera, in MuJoCo and on hardware.
  • Observation. The head-camera image and a 32-value robot state. No object state is given.
  • Action. 36 values at 50 Hz: hand, arm and waist targets, base height, and base motion. Pretrained GR00T Balance and Walk controllers drive the legs.
  • Scenes. Every episode draws new tools, positions, robot spawn, surface materials and lighting.
  • Environment IDs write decoy mode as R, for example G1BallMove-L1-R.

Overview

Choosing the right tool is only the first step

Humanoids need tools to do tasks beyond their physical limits. That takes selecting a suitable tool and coordinating manipulation and, when needed, locomotion. Existing benchmarks do not evaluate these together on a humanoid.

HumanoidToolBench does, with 18 tasks and ToolBook, 3.1k human demonstrations. Seven policies in simulation and three on the real robot show substantial gaps between selecting a tool and completing the task.

Limitations
  • The comparison uses one training run per policy, so variation reflects scenes and rollouts, not training seeds.
  • The real-robot study covers three policies on two L1 scenarios.
  • First contact is a proxy for the initial choice, and execution levels differ in layout as well as in locomotion.
  • The instruction probe uses one fixed IceBreak scene.
  • The LLM agent rows use 3 episodes per task, and the agents call a tool locator, inverse kinematics and a validated pick recipe that the policies do not have.

Open the repository in a coding agent and ask. The agent follows AGENTS.md from installation to the results table.

git clone https://github.com/SNU-PI/HumanoidToolBench.git
